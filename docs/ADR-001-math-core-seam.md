# ADR-001. Математическое ядро как один глубокий модуль

- **Статус:** принято
- **Дата:** 2026-10-14

## Контекст

Дипломный SPA: инвестор двигает ползунки и в реальном времени получает PD, грейд, вклад
каждого фактора, доходность с учётом риска и распределение результатов портфеля.
Расчётов много, они пересекаются: портфель использует индивидуальные PD, грейд выводится
из PD, текстовое резюме собирается из вкладов факторов. UI-слой React при этом должен
остаться тонким.

## Решение

Математика живёт в `src/domain/`. Наружу торчит **один seam**:

```ts
calculateAssessment(input: AssessmentInput): AssessmentResult
```

`AssessmentInput` = профиль заёмщика + условия сделки + (опционально) спецификация портфеля.
`AssessmentResult` = PD, грейд, логит, вклады факторов, сравнение с эталоном отрасли,
профиль для радар-чарта, расчёт доходности с вердиктом, текстовое резюме и результаты
портфельной симуляции.

### Почему один интерфейс, а не десять

- **Leverage.** UI вызывает один раз и получает всё для отрисовки дашборда. Вместо того
  чтобы знать про порядок вычислений, про пересчёт PD при смене отрасли и про согласованность
  `E(R)` с портфелем.
- **Locality.** Добавить фактор в модель = добавить его в калибровку и в разбор вкладов.
  Один файл спецификации признаков, а не пять мест в коде.
- **Тестируемость.** Тесты и UI пересекают одну и ту же границу — то, что тестируется,
  ровно то, чем пользуется приложение.

### Внутренние швы модуля (не входят в интерфейс)

`logit.ts`, `contributions.ts`, `grade.ts`, `expectedReturn.ts`, `riskProfile.ts`,
`portfolio.ts`, `narrative.ts` — это внутренние швы реализации. Они существуют, чтобы
`calculateAssessment` оставался читаемым, но наружу не выставляются: у них нет
потребителя, кроме самого модуля. Проверяются тоже через `calculateAssessment`.

По правилу «один адаптер — гипотетический шов, два — настоящий»: отдельный seam на
портфельную симуляцию **не** заводился. Симуляция — часть того же ответа на тот же вход,
поэтому новый публичный вход означал бы, что UI знает лишнее.

### Почему не Monte-Карло

Число дефолтов в портфеле — сумма независимых бернуллиев с разными вероятностями.
Её распределение считается **точно** пуассон-биномиальной рекурсией за `O(N²)`:
при `N ≤ 50` это микросекунды, результат детерминирован и тестируем. Монте-Карло дал бы
шум, который ухудшил бы скриншоты для защиты диплома.

## Последствия

- Тесты лежат в `src/domain/__tests__/assessment.test.ts` и проходят только через
  `calculateAssessment`.
- UI не содержит формул вообще. Добавить фактор в скоринг = добавить признак в
  `MODEL_CALIBRATION` и в `FACTOR_SPECS`.
- Модуль полностью чистый: нет `window`, `Math.random`, React, DOM. Тесты работают в `node`.

## Альтернативы

1. **Next.js + SSR.** Отклонено: расчёты клиентские, SSR ничего не даёт, а статический
   экспорт под GitHub Pages добавляет обвязку. Выбран Vite.
2. **Отдельный `riskLibrary` npm-пакет.** Отклонено как избыточное для одной команды
   и одного приложения.
